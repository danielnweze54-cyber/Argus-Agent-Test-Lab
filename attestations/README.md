# Argus registry — seals and finding records

A public, append-only, signed registry of what this lab has attested. Two
record types share one hash-chained log:

| Type | Attested fact | Lifecycle |
|---|---|---|
| `finding` | A defect exists in a third-party component, was disclosed by us at a named venue, and has a live status | open → acknowledged → fixed → verified-fixed / disputed / wont-fix; updates are **amendments**, never edits |
| `seal` | A run happened: SUT at commit X, scenarios S at pinned versions, experiments valid (verdicts), evidence hashes pinned, **full findings list attached** | Final at issuance |

**Neither record type attests bug-freeness.** A seal attests run validity and
findings completeness; findings are always attached, never hidden behind a
green verdict. The lab sells runs, not verdicts.

## Layout

- `records/NNNN-<slug>.<type>.json` — one signed record per file; `NNNN` is a
  global sequence across both types (a record number is a universal handle).
- `keys/argus-lab-2026q4.pub.json` — the lab's Ed25519 public key. The private
  key is NEVER in this repository.
- `INDEX.md` / `INDEX.json` — generated by `node tools/registry/build-index.mjs`,
  never hand-edited.

## Trust model

1. Each record is signed over its canonical JSON (sorted keys, no whitespace)
   with the lab key identified by `signer_key_id`.
2. Every record carries `prev_record_hash` = SHA-256 of the canonical form of
   the previous full record (genesis = `null`): the log is self-verifying even
   outside git, and git history provides the append-only guarantee on top.
3. Evidence entries of kind `file` pin SHA-256 of artifacts in this repo —
   editing the artifact breaks the seal's verification.
4. Verification is one command and exits non-zero on any tampering:
   `node tools/registry/verify-registry.mjs`

## Policy

- Findings against third-party projects are disclosed via the project's own
  public tracker before any record is issued; the record cites the venue.
- Finding records state facts and statuses neutrally; vendor responses and
  disputes are recorded as amendments.
- Self-runs are labeled `self_run: true`.
- Key rotation: new key gets a new `key_id` and a chain-linked amendment;
  old records stay valid under their original key.
- Roadmap: periodically anchor the chain head on-chain (the lab's own EVM
  adapters) so the log survives even a rewritten git history.
