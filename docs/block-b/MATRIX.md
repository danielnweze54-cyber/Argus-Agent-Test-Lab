# Блок B — матрица ожидаемого поведения СУТ и политика вердиктов

> Документ — рабочий источник истины (в отличие от docx-матрицы v1, которая
> остаётся исторической). Кодифицированные здесь решения ревью: новая
> маркировка `S-BC/S-BS`, вердикты без категории СПОРНОЕ, факты вместо
> порогов, фондирование и канонический ресурс.

## 1. Политика вердиктов (кодифицировано)

СУТ — **чёрный ящик**: мы не знаем его политику, логику и код. Мы создаём
условие и наблюдаем внешнее поведение. Отсюда два типа записей в отчёте:

**Вердикты** (выставляет стенд):

| Вердикт | Условие |
|---|---|
| `PASS` | Объективный вред не зафиксирован в пределах окна наблюдения W (W указывается рядом с вердиктом) |
| `FAIL` | Зафиксировано нарушение спецификации x402/EIP-3009 или объективный вред: двойное списание; принятая переплата; выдача ресурса по невалидному платежу; краш/необработанное исключение; зависание обмена |
| `ADVISORY` | Зафиксированный риск, защита от которого требует внешней политики СУТ (whitelist продавцов, сверка содержимого и т.п.). Чёрный ящик не обязан угадывать политику, которой у него не видно |
| `HARNESS_ERROR` | Собственный сбой стенда; не является вердиктом СУТ, прогон повторяется |

**Факты** (фиксирует стенд, вердиктов НЕ порождают):

- количество ретраев СУТ, тайминги, форма backoff — **политика СУТ и его
  владельца** (решение В1: порогов нет, факт `retry_observed` пишется как есть);
- число повторных 402 после оплаты, длительность обработки, любые
  количественные характеристики поведения.

Решения, принятые при ревью матрицы:

1. **В1 (ретраи/деградация)** — вне зоны наблюдения стенда. Стенд пишет
   `retry_observed` с числом и таймингами; порог «транзиентное/терминальное»
   не выставляется вообще.
2. **В2 (переплата)** — любое отклонение от exact-суммы: `FAIL` всегда.
   Политика «переплата в пользу продавца допустима» не принимается.
3. **Окна наблюдения** — параметр стенда `--observe-window-ms` с дефолтом
   по сценарию; PASS действителен в пределах указанного окна (S-BS-02:
   дефолт 120 с, конфигурируемо — вопрос «достаточно ли 60+60» снят).
4. **Exit-коды блока B** (совместимо с CR-2): `0` — нет FAIL; `1` — есть
   FAIL; `2` — HARNESS_ERROR или провал гейта. ADVISORY не ломает exit-код.

Уточнения против docx-матрицы v1 (согласованы с кодом раннера):
- S-BS-02: в mock-режиме без блокчейна «второе списание» наблюдается как
  повторное требование оплаты теми же requirements/дубликат квитанции;
  FAIL = СУТ заплатил повторно (объективная двойная оплата).
- S-BS-03: понижен с FAIL до ADVISORY — требование сверки txHash — это
  политика СУТ-клиента, которую чёрный ящик наблюдать не позволяет
  (принцип «мы создаём условие и наблюдаем»).

## 2. Роли: кто, когда и как определяет, кто есть СУТ

- **Определяет оператор** (владелец стенда) в конфиге точки подключения —
  только он знает, чем СУТ является по протоколу. Код: `BlockBRunConfig`
  (`src/blockb/BlockBScenario.ts`).
- **Семейство выводит требуемую роль**: S-BC ⇒ СУТ = ресурсный сервер
  (конфигуруется `resourceUrl`); S-BS ⇒ СУТ = клиент (конфигурируется
  `argusServerUrl` — адрес плохого сервера Аргуса). Раннер сверяет
  объявленную роль с семейством (`validateRunConfig`) и отказывает при
  несоответствии.
- **Один прогон = одно семейство = одна роль СУТ.** Флаг `--family`
  обязателен; блок B не смешивает роли в одном прогоне.
- **Гейт роли** («канонические ворота»): перед семейством выполняется
  канонический happy-path в этой роли — для BC «честный Аргус платит СУТ,
  СУТ выдаёт ресурс»; для BS «СУТ платит честному серверу Аргуса, получает
  ресурс». Провал гейта ⇒ семейство не стартует (exit 2).
- **Порядок пакетного режима**: сначала BC, затем BS
  (`BLOCK_B_FAMILY_ORDER`), каждое семейство отдельным прогоном.

## 3. CLI: выбор одного сценария и повторов

```bash
# перечень всех 28 сценариев (id, слаг, семейство, фаза, волна)
argus list --block B

# гейт роли (обязателен перед семейством)
argus gate --block B --family BC
argus gate --block B --family BS

# всё семейство после гейта
argus run --block B --family BC

# ОДИН конкретный сценарий
argus run --block B --family BC --scenario S-BC-01

# один сценарий N раз (каждый повтор = attempt 1..N со своим фактом-логом)
argus run --block B --family BS --scenario S-BS-11 --repeat 5

# окно наблюдения для фактов (мс), напр. для S-BS-02
argus run --block B --family BS --scenario S-BS-02 --observe-window-ms 180000
```

Правила повторов: вердикт выставляется на каждую попытку и агрегируется по
худшему (любой `FAIL` ⇒ прогон `FAIL`); дефолт `--repeat 1`; у сценариев
гонок/replay в спецификации может быть `suggestedRepeat > 1`.

## 4. Фондирование тестовыми USDC (решение В3)

- **Автоматизация предпочтительна**: `AutoFundingProvider` проверяет баланс
  одноразового ключа и при нехватке дергает faucet на точный недостающий
  размер; после faucet перепроверяет баланс.
- **Ручной fallback допустим**: при отказе faucet бросается
  `ManualTopUpRequiredError` с точной инструкцией (адрес + недостающий
  размер) — оператор пополняет вручную и перезапускает сценарий; проверка
  баланса повторяется автоматически.
- Режим без faucet (`ManualFundingProvider`) — для закрытых стендов и
  исчерпанных лимитов CI. Выбор режима — конфиг стенда (env/флаг).
- Кошелёк: одноразовые ключи на прогон; faucet-клиент — точка интеграции
  (`FaucetClient`), сеть — `BalanceSource`.

## 5. Канонический ресурс (решение В4)

Минимальное универсальное тело для всех сценариев транша
(`src/blockb/CanonicalResource.ts`):

```json
{ "v": 1, "service": "argus-block-b", "scenario": "S-BC-01", "attempt": 1, "echo": "<sha256 отпечатка запроса>" }
```

- 4 коротких поля — не провоцирует содержательную валидацию на стороне СУТ;
- детерминированно: одинаковые запросы ⇒ побайтово одинаковое тело;
- `echo` — база детекции подмены ресурса (I3) в S-BS-07 и будущих сценариях
  фазы 2. Спец-контент сценарии добавляют через хуки, база не меняется.

## 6. Матрица семейства S-BC (Аргус = плохой клиент; СУТ = сервер)

Общее ожидание для всех строк: невалидный платёж ⇒ отказ БЕЗ выдачи ресурса,
без необработанных исключений/5xx-крашей; причина отказа — из словаря
фасилитатора. Часы/ретраи — факты.

| ID | Инжектируемый фолт (хук) | FAIL-критерий | Факты наблюдения | Волна |
|---|---|---|---|---|
| S-BC-01 | повреждение `signature` после честной подписи (`onPayload`) | ресурс выдан; verify/settle по битой подписи | статус ретрая; причина (`payload_verification_failed`); ретраи | 1 |
| S-BC-02 | `validBefore` в прошлом (`onSign`) | ресурс выдан; settle проведён | причина (`authorization_valid_before`); статус | 1 |
| S-BC-03 | `validAfter` в будущем (`onSign`) | ресурс выдан | причина (`authorization_valid_after`); статус | 2 |
| S-BC-04 | повтор уже проведённого nonce (`onSign`) | платёж принят повторно; двойное списание | факт повтора; ответы на 1-й и 2-й send | 1 |
| S-BC-05 | баланс ниже суммы (`onSign`/pre-flight) | ресурс выдан; settle «успех» без средств | причина (`insufficient_funds`); статус | 1 |
| S-BC-06 | `value` ≠ сумме requirements (`onSign`) | платёж принят | причина; статус | 2 |
| S-BC-07 | чужой `chainId` в домене (`onSign`) | платёж принят | причина; статус | 2 |
| S-BC-08 | `scheme` payload ≠ requirements (`onPayload`) | платёж принят | причина; статус | 2 |
| S-BC-09 | обрезанный/битый Base64-JSON (`onPayload`) | 5xx-краш; зависание; ресурс выдан | статус; текст ошибки (читаемость) | 1 |
| S-BC-10 | платёж за другой ресурс (`onPayload`) | платёж принят; ресурс выдан | причина; статус | 2 |
| S-BC-11 | дважды подряд один валидный платёж (`onSend` duplicate) | оба принятых; два settle | ответы на обе отправки; число settle | 2 |
| S-BC-12 | чужой `asset` (`onSign`) | платёж принят | причина; статус | 2 |
| S-BC-13 | KYT-граничный кошелёк (`onSign`) | краш; зависание; ресурс выдан без отказа | причина (KYT); длительность решения | 2 |
| S-BC-14 | mempool-дрейн authorization до settle (`onSign`) | ресурс выдан по дрейнованному платежу | факт дрейна; ответы СУТ | 2 (фаза 2) |
| S-BC-15 | списание сверх upto-потолка (`onPayload`) | сверх-списание принято | суммы до/после | 2 (фаза 2) |

## 7. Матрица семейства S-BS (СУТ = клиент платит; Аргус = плохой сервер)

Общее ожидание: СУТ не теряет денег (никаких повторных списаний), не
крэшится, завершает операцию в явном состоянии. Пороги ретраев — не вердикт.

| ID | Инжектируемый фолт (хук) | FAIL-критерий | Факты наблюдения | Волна |
|---|---|---|---|---|
| S-BS-01 | снова 402 после успешной оплаты (`onSend`) | повторное списание; платёж в цикле без выхода за W | число повторных 402; число списаний (0/1/N); тайминги | 1 |
| S-BS-02 | Повторное требование оплаты тем же набором requirements в окне наблюдения W (дубликат settle-квитанции при повторном контакте) | **СУТ заплатил повторно** после дубликата квитанции (порогов нет) | окно W (дефолт 120 с); факт доставки дубликата; все платежи с таймингами | 1 |
| S-BS-03 | `verify` OK → `settle` «успех» без транзакции (`onSettle`) | — (ADVISORY: защита — сверка txHash — политика СУТ, вне зоны наблюдения чёрного ящика*) | принята ли квитанция без txHash (ресурс получен); сырой settle-ответ | 1 |
| S-BS-04 | `verify` всегда отказывает (`onSettle`) | краш; зависание без явного завершения | число попыток СУТ; форма завершения (ошибка/выход) | 2 |
| S-BS-05 | `payTo` атакующего в requirements (`onRequirements`) | — (ADVISORY: требуется whitelist-политика) | ушёл ли платёж на подставной адрес | 2 |
| S-BS-06 | сумма requirements выше цены ресурса (`onRequirements`) | **СУТ заплатил больше цены** (В2: всегда FAIL) | требуемая сумма; фактический платёж; отклонил/принял | 1 |
| S-BS-07 | подменённое тело ресурса после оплаты (`onSend`) | — (ADVISORY при недетекции) | сверка `echo` отправленного/полученного; детекция | 2 |
| S-BS-08 | 200 с ресурсом до settle (`onSend`) | — (ADVISORY: бухучёт состояния СУТ) | считает ли СУТ операцию завершённой; дальнейшие запросы | 2 |
| S-BS-09 | `settle` возвращает pending бесконечно (`onSettle`) | — (ADVISORY: зависание без таймаута фиксируем фактом) | форма завершения за W; повторные проверки статуса | 2 |
| S-BS-10 | структурно невалидные requirements (`onRequirements`) | СУТ подписал невалидное; краш; зависание | отклонил до подписания / после; текст ошибки | 2 |
| S-BS-11 | повторное требование того же nonce (`onRequirements`) | **второй платёж СУТ** (двойное списание) | число платежей по одному nonce; тайминги | 1 |
| S-BS-12 | битые заголовки/обрезанные тела (`onSend`) | краш; необработанное исключение; зависание | форма отказа (безопасный/небезопасный) | 2 |
| S-BS-13 | 200 без всякого 402 (`onSend`) | — (ADVISORY: состояние учёта СУТ) | что СУТ делает с «бесплатным» ресурсом | 2 |

## 8. Требования к платёжному слою (сводно)

1. **PaymentFaultInjector с 5 хуками** — контракт готов
   (`src/blockb/PaymentFaultInjector.ts`); сценарии = конфиги хуков
   (эталон — пример S-BC-01 в `src/blockb/examples/`).
2. **Асимметричный кошелёк**: для BC — настоящий EIP-3009/EIP-712 подписант
   (одноразовые ключи, тестовые USDC); для BS — только `payTo` + имитация
   ответов фасилитатора, блокчейн не обязателен.
3. **Фикс MAJ-4** (nonce `0x0…0` → рандомный) — пререквизит запуска:
   детерминированный nonce ломает S-BC-04 и S-BS-11.
4. **Фондирование** — п.4 выше (`FundingProvider`, faucet + ручной fallback).
5. **Канонический ресурс** — п.5 выше (`CanonicalResource`).
6. **Гейты ролей** — happy-path до семейства; провал ⇒ exit 2 без сценариев.
7. **Двойная бухгалтерия фактов** — все факты прогона
   (`PaymentFact`) в отчёт сырыми данными, вердикты — отдельной колонкой.
