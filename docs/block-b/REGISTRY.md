# Блок B — полный реестр сценариев (33)

> Источник истины по маркировке и составу. Устаревшая маркировка
> `S-B-BC-NN` / `S-B-BS-NN` заменена на `S-BC-NN` / `S-BS-NN` (буква блока
> `B` из ID исключена, нумерация сохранена 1:1). Ранние документы (docx-матрица
> v1) читаются по старой маркировке; в коде принимается только новый формат
> (`validateScenarioId` в `src/blockb/BlockBRoles.ts`).

## Роли и семейства

| Семейство | Аргус | СУТ | Что наблюдаем |
|---|---|---|---|
| **S-BC** | плохой клиент | ресурсный сервер (принимает платежи) | как СУТ отклоняет/принимает платежи и выдаёт ресурс |
| **S-BS** | плохой сервер | клиент (платит за ресурс) | как СУТ защищает свои деньги и своё состояние |

Инвариант: **в одном прогоне СУТ исполняет ровно одну роль**. Кто есть СУТ,
объявляет оператор в конфиге точки подключения; раннер сверяет роль с
семейством и отказывает в запуске при несоответствии. Семейства никогда
не смешиваются в одном прогоне; порядок пакетного режима: сначала BC,
затем BS, каждое — со своим гейтом (канонический happy-path роли).

### Capture notes v2 (2026-10-22, follow-up к замечаниям ревьюера по #3866)

Дисциплина доказательств (держать различие во всех сводках):
**установлено** — клиент подписал и передал EIP-3009 авторизацию на
завышенную сумму (числа signer-вызовов и значения сняты на границе
подписанта); **НЕ установлено** — on-chain переплата: settle в харнессе
моковый (стенд фолт-инжекции, не фасилитатор), кошелёк СУТ — разовый
нефондированный ключ, перенос средств невозможен; при совместимом
фасилитаторе захваченная авторизация ушла бы в сеть как есть.

Пробы волны 2.1 (`--requirement-amounts A1,A2` + инструментированный
SUT-клиент v2, стенд oversize-amount):

- **C1** (принятая котировка НЕизменена, `10000,10000`): обе итерации
  оплачены по 10000, 2 signer-вызова — «неизменённая принятая котировка
  работает».
- **C2** (переименован 2026-10-24 по замечанию ревьюера: «raised-requirement
  second PAID cycle» — два ЗАВЕРШЁННЫХ оплаченных цикла, оба settle'ятся на
  стенде; НЕ неопределённый ретрай одной операции; потерянный ответ —
  отдельный контроль L1-CTL, см. capture notes v3) (принятая котировка →
  ×10 во втором цикле, `10000,100000`, observe): текущий клиент вызывает
  подписанта на 100000 ПОСЛЕ принятия 10000 — binding-проверки нет (корень
  дефекта #3866); стенд получил оба платежа.
- **C2-CTL** (предложенный ревьюером контроль): отказ ДО вызова подписанта

- **H1** (сумма СВЕРХ spend-капа: `5000000` = $5 при капе $1): подписант

  требования до подписанта; кап — потолок, а не ожидание цены (между
  принятой ценой и капом сумма никем не проверяется).
- **E1** (ниже капа `50000` ≠ ожиданию вызывающего `10000`): отказ на

### Волна 3 (2026-10-24, живой прогон): переносы демо-сценариев на x402

Пара «новых» сценариев, придуманных и исполненных для демок вне x402-рельс,
перенесена на официальный стек @x402/* v2.28.0 и прогнана живьём

  payload нет ни у клиента, ни в протоколе. Контроль s10_c1 (тот же флоу

  подписание + передача authorization, не on-chain перевод).
- **S-BS-17 `over-budget-x402`** ← Block D S11 OverBudget (fiat).
  Бюджетный контроллер ВЫЗЫВАЮЩЕГО в client_v4 (`SUT_CLIENT_BUDGET_ATOMIC`):
  отказ ДО подписанта (`budget_exceeded_before_signer`), boundary ровно на

- **S-BS-18 `first-accept-wins`** ← S-ZS-02 zeus-secretariat (malicious

### Волна 2.5 (2026-10-25, пробы лаборатории A10/A11 → S-BS-14/15)

**Attribution: executed per the Argus Agent Test Lab scenario series
(A10–A11 → S-BS-14/15). Any reuse or derivative MUST retain this banner.**

Происхождение: лабораторные пробы A10a/A10b/A11, прогон 2026-10-25,
x402-foundation/x402 PR #3920 @ 2b4cc47, референс-риг лаборатории
`test/lab/matrix-a10a11.extension.test.ts` (TS/vitest). Вердикт
прогона-источника: обе пробы сработали = СУТ (клиент) ПРОВАЛИЛ обе проверки —
это диагноз коду (красная зона), НЕ дефект стенда: ожидаемый результат
против 2b4cc47 — FAIL по обоим сценариям. Правило вердикта — SUT-perspective:
сработавшая проба = провал СУТ; PASS = СУТ удержал. Фиксация FAIL —
«candidate-fix boundary» (граница фикса, не evidence of exploitation:
settle моковый, перенос средств невозможен).

Перекрёстная карта (обязательна в обе стороны; A-номера остаются внешними
именами проб — словарь подхвачен третьими лицами: аудитором и контрибьютором;
S-BS-ID — постоянные дома в реестре):

| Проба acceptance-слоя | Постоянный дом в реестре |
|---|---|
| A10a (гонка, explicit expectation) | S-BS-14, вариант explicit |
| A10b (гонка, first-accepted) | S-BS-14, вариант first-accepted |
| A11 (неатомарная сумма мимо пина) | S-BS-15 |

Размещение: почему S-BS, а не S-BC — в A10/A11 СУТ — клиент, защищающий свои
деньги (фикс PR #3920 — клиентские spend-controls): это определение роли
S-BS («СУТ платит, Аргус принимает»); в S-BC роль обратная. Прецедент роли —
S-BS-06, родительская находка #3866. Почему не новый B4-блок: B4-блоки —
старая классификация S1–S8 по топологии; батарея Block B — действующий
реестр с раннером и оценщиками. Оба сценария живут в той же топологии
(клиент → мок-сервер; фасилитатор не нужен — пробы до подписи).

Новые оси покрытия (чего не было в реестре):
- **S-BS-14** — (1) concurrency на инициализации клиентского состояния:
  два КОНКУРЕНТНЫХ набора requirements на один ключ квоты (resource, scheme,
  network, asset) при пустом биндинге, расхождение payTo (обязательный
  вектор; first-accepted — ещё и amount). Оракул — счётчик вызовов
  подписанта (единственный pre-signature; читается после обеих попыток,
  параллель = Promise.allSettled). Контрол-1 (последовательная пара, свежий
  клиент: ровно 1 вызов, typed-отказ до подписанта) и контрол-2 (параллельные
  ИДЕНТИЧНЫЕ попытки: 2 подписи, no false positive) обязательны и входят в
  вердикт (контрол-1 красный = FAIL; контрол-2 красный = ADVISORY — деньги
  целы, легитимный поток сломан). Ловушка рига: билдер предложений может
  иметь СВОЙ дефолт payTo — проставлять детерминированно (у лаборатории было
  3 ложных срабатывания на первом прогоне); свежий клиент на каждую итерацию
  и на каждый контрол.
- **S-BS-15** — (2) канонизация представления суммы мимо включённого
  expectation-чека: amount "0.5" (неатомарная десятичная форма) при пине
  "10000" ($0.01). Главная ловушка: наивный вариант «сумма сверх капа»
  ЛОВИТСЯ КАПОМ и выглядит «безопасно» — ложный отрицательный; окно
  эксплойта — только ПОД капом; тройка вариантов обязательна (подкаповая
  десятичная / сверх-каповая "2.0" = $2 — кап-щит / атомарный дубль
  "500000" = $0.50 — чек). createPaymentPayload РЕЗОЛВИТСЯ УСПЕХОМ —
  утверждение инспектирует payload.amount, не catch (catch-паттерн дважды
  давал ложный PASS). Сравнение сумм — по десятичному эквиваленту
  (scale 10^decimals; `decimalToAtomic`), не по строке; payTo не варьировать.

Канон разбора сумм `decimalToAtomic` (один на оценщик и оракул):
целочисленная строка = атомарная форма ("10000" = $0.01, "500000" = $0.50);
дробная = неатомарное представление → scale ("0.5" → 500000); прочие формы
("1e6", hex, знак, дробь за пределами точности) — null; кандидаты карт
S-BS-15b/c (unprobed).
